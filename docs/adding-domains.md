# ドメインの増やし方

ドメインは知識の境界です。ここを間違えると、システムは「なんでも入っている引き出し」になって使えなくなります。

## いつ作るか

**作る**：同じ種類の問いや仕事が**繰り返し**発生していて、そのたびに同じ文脈を説明し直している。判断の材料が複数回にわたって積み上がる。

**まだ作らない**：一度きりの話題。既存ドメインの1ファイルで足りるもの。「いつかやるかもしれない」もの。

空のドメインは負債です。中身の入った1つは資産です。**最初は1つだけ**にしてください。

## 粒度の決め方

粒度に迷ったら、この問いで決めます。**「このドメインの `index.md` は、どんな問いに常に答えられるべきか？」**

- 答えが1つの文で言えるなら、粒度は正しい。
- 答えが「いろいろ」になるなら、大きすぎる。分ける。
- 答えが月に1回も必要にならないなら、小さすぎる。親ドメインの1ファイルにする。

例：`work`（大きすぎることが多い）→ `work-ops`（案件・単価・営業）と `career`（方向性の判断）に分ける、など。ただし**分けるのは実際に困ってから**。

## 作り方

`add-domain` と打ってください。次のことが起きます。

1. `knowledge/domains/<slug>/` に3つのファイルができる（README、index、intentions-log）。
2. README の**知識ポリシー**を対話で埋める。ここが一番大事です（下記）。
3. `knowledge/index.md` に登録される。
4. Tier-0に出すべきなら `state.md` にも載る。

## 知識ポリシーが重要な理由

ドメインごとに「考え方」が違います。同じやり方で処理すると必ず壊れます。

| ドメインの例 | 入力 | 考え方 | 陥りがちな罠 |
|---|---|---|---|
| 仕事・案件 | 面談メモ、見積、契約 | 帳簿的に。数字と日付を正確に | 感想を事実として書く |
| コミュニティ | 複数人の会話ログ | 人類学的に。誰が何を言ったかの文脈ごと | 多数意見を「決定」にしてしまう |
| 日記 | 本人の生の声 | 保存。言い換えない | 要約して声を殺す |
| リサーチ | 外部の動画・記事 | 蒸留。原理だけ残す | 要約を自分の事実として扱う |
| 健康 | 体感、検査値 | 仮説と検証。時系列で | 一度の体感を結論にする |

このポリシーがあると、`closeout` や `grill` のときに「このドメインではどう畳むか」が自動的に決まります。

## 機微な内容の扱い

実際の財務、取引先データ、契約の詳細のような機微な内容は、**別のプライベートリポジトリ**に置き、こちらには機微でない**ポインタのドメイン**だけを置くこともできます。`docs/knowledge-accumulation-strategy.md` を参照。

## 使わなくなったドメイン

消さないでください。`state.md` の「停止中」に移し、README の状態を「保留」にします。過去の判断の記録は、後から効いてきます。
