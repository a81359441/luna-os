# セキュリティと運用上の限界

luna-osは個人で知識と作業を管理するためのテンプレートです。ここでは、現在のコードと設定で保証できる範囲、運用上の規律に頼る部分、企業で利用する際に追加する対策を分けて説明します。

## 実装と権限で保証できること

以下は、同梱コードを変更せず、該当する設定や権限が有効な場合の制限です。AIが利用できる他のツールや、端末全体の動作まで制限するものではありません。

### Gmailの権限と操作

| 対象 | 制限とその範囲 |
|---|---|
| 既定の認証 | [`auth.py`](../bin/gmail/auth.py) は `gmail.readonly` だけを要求します。この権限だけのトークンでは、Gmail APIで送信・下書き作成・メールの変更や削除はできません。 |
| 追加の権限 | `--compose` は `gmail.compose`、`--modify` は `gmail.modify` を追加します。どちらも送信を許可するため、追加後はスコープによる送信禁止を保証できません。両方の指定も可能です。 |
| 読み取り処理 | [`gmail.py`](../bin/gmail/gmail.py) のGmail API呼び出しはGETのみです。認証トークンの更新には、別途OAuthエンドポイントへのPOSTを使います。 |
| 受信箱の整理 | [`tidy.py`](../bin/gmail/tidy.py) は `messages/batchModify` でラベルを付け外しします。アーカイブは `INBOX`、既読化は `UNREAD` を外す操作です。指定したラベルがなければ `labels` へのPOSTで作成します。既定はドライランで、変更するには `--apply` が必要です。 |
| 送信・下書き作成・メール削除 | 同梱コードにこれらの処理はありません。ただし、追加権限を持つトークンで別のコードやツールを使うことまでは防げません。 |

スコープの権限は [Googleの公式仕様](https://developers.google.com/workspace/gmail/api/auth/scopes)に基づきます。認証方法と使い方は [Gmail連携のREADME](../bin/gmail/README.md)を参照してください。

`tidy.py` の `--apply` は実行の切り替えであり、人間が承認したかを検証する機能ではありません。メッセージIDと操作は `.session/gmail-tidy.log` に記録され、`unarchive --apply` で直前のアーカイブを戻せます。すべての操作を元に戻す機能や、改ざんを防ぐ監査ログではありません。

### 認証情報とGit

[`auth.py`](../bin/gmail/auth.py) はトークンをJSONファイルに保存し、ファイルの権限を `0600` に設定します。既定の保存先は `.secrets/gmail-token.json` で、worktreeでは本体のチェックアウトを参照します。保存先は環境変数でも変更できます。暗号化して保存する実装ではありません。

[`.gitignore`](../.gitignore) は `.secrets`、`data/`、`.session` などを通常のGit追加対象から除外します。すでに追跡されたファイルや強制追加、別の場所へのコピー、他のツールによる読み取りや外部送信は防ぎません。gitignore対象であることは、端末の外に出ない保証にはなりません。

### フックによる制限

[`.claude/settings.json`](../.claude/settings.json) に登録された [`no-bulk-git-add.sh`](../.claude/hooks/no-bulk-git-add.sh) は、Claude CodeのBashツールが実行するコマンドをパターンで検査し、`git add .` や `git add -A` などを拒否します。シェル構文全体を解析するものではなく、検出範囲に限りがあります。フックを通らない操作には効きません。

並行セッションや編集後の長いダッシュに対する警告は、作業の分離や変更の取り消しを自動で行うものではありません。各フックの条件と役割は [SETUP.mdの「フックの確認」](../SETUP.md#4-フックの確認)に記載しています。

## 運用上の規律に頼っていること

運用ルールの正本は [`CLAUDE.md`](../CLAUDE.md) です。以下はAIへの指示と人の確認で守る方針であり、コードで一律に強制しているわけではありません。

- **変更の承認**：新しく残す知識は原則としてブランチ上で提案し、ユーザーの承認をマージで反映します。「仕事の進め方」では、小さく明白な追加は短いブランチの即マージ、または `main` への直接変更も認めています。フックは承認の有無を検証せず、未承認の書き込みやマージを止めません。Git履歴だけでは、人が承認した証拠にはなりません。
- **知識の正確さと境界**：ファイルを根拠に回答し、個人・商用・発信の文脈を混ぜる前に確認する方針です。ファイルが正しいことや、AIが出典と境界を守ることの自動検証はありません。
- **外部の文章の扱い**：メールやウェブページを指示ではなくデータとして扱うルールです。プロンプトインジェクションを完全に防ぐ技術的な隔離ではありません。
- **メールの送信と保存**：送信は人間が行い、生のメールを知識の索引に入れず、必要な事実だけを確認して残す方針です。個人情報の自動除去や、書き出し先を `data/` に限定する処理はありません。
- **フックによる指示の再注入**：`slow-mode.sh` や `domain-stance.sh` などは、条件に応じてAIの文脈に指示を追加します。指示に従うことや、確認まで処理が止まることを保証しません。

## 企業利用で追加が必要なこと

企業の情報を扱う場合は、導入側で次の対策と運用を設計する必要があります。このテンプレートのルールだけで、組織の承認や情報管理の要件を満たすものではありません。

- **承認を強制する仕組み**：保護ブランチ、必須レビュー、直接pushや保護設定の迂回を制限する権限設計。AIの書き込み権限と、人が承認する権限も分けて検討します。
- **実行環境と接続先の制限**：AIが使えるツール、ファイル、ネットワーク、OAuthスコープを用途に応じて絞ります。送信禁止が要件なら、送信コードを同梱しないだけではなく、送信できる権限を与えない構成が必要です。
- **機密情報と認証情報の管理**：組織が認めたAIサービスや契約・設定を使い、入力してよい情報、保存先、閲覧者、保持期間、削除手順を決めます。認証情報の保管・失効・更新、秘密情報のコミット検知も別途整えます。
- **監査と復旧**：誰が何を承認し、どの操作を行ったかを追跡できる記録、記録へのアクセス制御、バックアップと復旧手順を用意します。ローカルのGit履歴やログだけを、改ざんできない監査記録とは扱わないでください。
