# 仕事の流れ

このシステムを「プロンプト集」から「信頼できる運用基盤」に変えるための流れです。意図的に単純にしてあります。すべての仕事は、受付され、出典が確定し、実行され、レビューされ、閉じるか真実の更新になるか、のどちらかで終わります。

## 全体像

| 段階 | 担当 | 結果 |
|---|---|---|
| **1. 受付** | マスター | 依頼を明確にし、分類する。 |
| **2. 振り分け** | マスター | 担当・ドメイン・参照ファイルを決める。 |
| **3. 発注** | マスター / ユーザー | 非自明な仕事は明確なタスクの形にする。 |
| **4. 実行** | 担当エージェント | 承認済みソースだけを使って成果物を作る。 |
| **5. レビュー** | マスター / ユーザー | 根拠・有用性・リスクを点検する。 |
| **6. 真実の更新** | 司書 | durable な知識をMarkdownの提案として出し、承認を得る。 |
| **7. 締め** | マスター | 結果・変更ファイル・決定・次の一手をまとめる。 |

## 1. 受付

読み込み済みのファイルで答えられる質問は、出典を付けてその場で答えます。複雑な仕事は、担当と成果物が明示されたタスクにします。

| 依頼の型 | 既定の扱い |
|---|---|
| 読み込み済み知識からの即答 | 出典つきで直接答える |
| ドメイン固有の計画 | 該当ドメインで扱う |
| リポジトリの整理 | 司書 |
| 自動化・定例化・連携 | オペレーション |
| 発信・マーケ・原稿 | グロース（ドメインの事実で裏付ける） |
| ドメイン横断の戦略 | マスターが持つ |

## 2. 振り分け

振り分けは明示的に述べます。実際には分かれていない仕事を、複数エージェントが働いているように見せない（エージェントごっこ）。最低限の宣言：

```markdown
モード: <エージェント>
理由: <なぜこの担当か>
ソース: <読み込んだ / 必要なファイル>
成果物: <何を出すか>
限界: <未検証の点>
```

必要なファイルが無いなら、ユーザーに求めるか、「ナレッジベースに検証済みの情報がありません」と言います。

## 3. 発注

複雑・恒久的・委譲される・リポジトリを変更する仕事には発注書を作ります。良い発注書に含まれるもの：担当ラベル、一文のタスク、参照してよいファイル、**やらないこと**、完了条件、承認者。

## 4. 実行

実行中は、種類ごとに扱いを変えます。

| 出力の種類 | 必要な扱い |
|---|---|
| **検証済みの事実** | 出典を示す |
| **分析** | どの事実・仮定に依存しているかを述べる |
| **仮定** | 仮定だと明記する。真実として書かない |
| **新しい知識** | Markdownの提案として出し、承認を得てから真実にする |
| **リポジトリ変更** | 変更ファイルと理由をまとめる |

## 5. レビュー

| 観点 | 問い |
|---|---|
| **根拠** | ドメインの事実に出典が付いているか |
| **範囲** | 役割とドメインの内側に留まったか |
| **有用性** | 実際の依頼に答えているか |
| **リスク** | 規約・プライバシー・金銭・法務・運用のリスクを表に出したか |
| **恒久性** | 真実として残すべきものはあるか |

## 6. 真実の更新

durable な知識はチャットに置き去りにせず、リポジトリに移します。司書が正確なMarkdown変更を提案し、関連する索引を更新し、既存の知識と提案中の知識をはっきり分けます。

**ユーザーが承認し、正しいファイルにコミットされるまで、どの提案も検証済みにはなりません。**

## 7. 締め

非自明な仕事はすべて締めで終わります。担当、やったこと、変更・提案したファイル、未解決の問い、次の一手。`closeout` スキルがこれを実行します。

## 宣言 → タグ → 確認

文脈が混ざる依頼のためのチェックリスト。

1. **宣言**：想定される分かれ目を平易な言葉で。個人の文脈、商用の文脈、関係するファイル・リポジトリ。
2. **タグ**：`#個人` `#商用` `#発信` `#複合`。
3. **確認**：書く・移す・コミットする前に持ち主を確認する。曖昧なら先に聞く。

個人の素材をプロジェクトのリポジトリへ、あるいはプロジェクトの実行詳細を個人ファイルへ、確認なしに越境させません。

## 文脈の読み込み規律

最小限の有用な文脈を読み込みます。`state.md` → `knowledge/index.md` → 該当ドメインの `index.md` → 直近の `intentions-log.md`。それより深いファイルは必要になってから。

## アンチパターン

| アンチパターン | なぜ危険か | 正しい振る舞い |
|---|---|---|
| **エージェントごっこ** | 実際には分かれていない仕事を分かれているように見せると、信頼が落ちる | 本当にスコープが分かれるときだけ複数使う |
| **チャットを記憶にする** | 履歴は監査できず、誤って思い出す | durable な知識はMarkdownにコミットする |
| **無制限の専門家** | 曖昧なエージェントは越境して捏造する | 登録済みの明確なスコープで使う |
| **黙って真実を変える** | ユーザーが真実の管理者でなくなる | 提案して承認を得る |
| **ドメインの混線** | ある領域の事実が別の領域を汚染する | 混ぜる前にマスターへ戻す |

## 複数エージェントの連携

本当に複数必要なときは、自由な同時進行ではなく**順番**にします。各受け渡しで、入力・必要な出力・未解決のリスクを明示します。

```markdown
受け渡し1: <ドメインエージェント> → <グロース>
入力: 検証済みの事実（製品、ポジショニング、規約）
必要な出力: 規約を破らない企画案
未解決リスク: 主張の根拠、チャネルの前提

受け渡し2: <グロース> → マスター
入力: 企画案と理由
必要な出力: 最終推奨と、必要なら真実の更新提案
未解決リスク: 予算、時期、承認
```
