# ドメインを追加する

出典を辿れる、きれいなドメインを作ります。最小限に留めること。中身は後から、根拠と承認を伴って入ります。

**忘れられるのは「登録」です。** ディスク上には存在するのに `DOMAIN_LABELS` に無いドメインは、スタートメニューでもステータスバーでも**生のスラグのまま**表示されます。手順3のチェックリストは、全部やること。

## 手順0: 入れ子にするか、分けるか

何か作る前に、どちらの形かを決めます。

- **入れ子**（`knowledge/domains/<親>/<子>/`）にするのは、子が**親と同じ主題の一部**であるとき。サブドメインは自分の `index.md` と `intentions-log.md` を持ち、自分の出典パス（`domains/<親>/<子>/<file>.md`）を持ちます。
- **横に並べる**（`knowledge/domains/<名前>/`）のは、**たまたま同じフォルダに同居していただけの別の主題**であるとき。「職歴」は「就職活動」の一部ではありません。**並べるほうが既定です。**

膨らみすぎたドメインを分けるなら、ファイルに触る前に、そう言って、分割後のドメイン名を挙げること。分割は真実の構造の変更なので、良い理屈ではなく**承認**が要ります。

**既知の制限:** `bin/menu` が並べるのは最上位のフォルダだけなので、サブドメインはスタートメニューから直接は選べません。親から辿ります。

## 手順1: 作る前に確認する

- **名前**（kebab-case のフォルダ名。例 `inbound-tourism`）と**一行の目的**。
- **状態**: 稼働中 / 保留 / 提案。
- **知識ポリシー**: このドメインが**どう考えるか**を聞く。どんな素材が入ってくるか、どんな思考様式で処理するか、`index.md` が常に答えるべきことは何か、何を捨てるか、このドメイン特有の罠は何か。**発明しないこと。** ポリシーを当て推量で決めたドメインは、その後ずっと間違った形でコンパイルされ続けます。
- **`## Stance` は作る時点では書かない。** スタンス（このドメインで AI がユーザーとどう一緒に考えるか、最大5行、`domain-stance` フックが毎ターン注入する）は、ドメインを実際に使い、AI が一度読み違えたあとに書く。推測で書いたスタンスは、毎回の発言に注入されるノイズになります。
- **境界チェック**: 機微な内容や商用の内容（実際の財務、取引先データ、顧客名）は、別のプライベートリポジトリに置き、ここには機微でないポインタだけを置く（`docs/knowledge-accumulation-strategy.md`）。
- **ブランチで作業する。** このチェックアウトで他のセッションが動いているなら worktree を切る（`git worktree add ../work-<topic> -b work/<topic>`）。

## 手順2と3は、まず `bin/new-domain` で

```bash
bin/new-domain <slug> <表示名> "<一行の目的>" [--lane <レーン名>]
```

雛形の複製、`knowledge/index.md` の2箇所、`state.md`、`DOMAIN_LABELS`、（`--lane` を付ければ）`LANES` を1回で済ませます。`--dry-run` で何も書かずに確かめられます。そのあと README の知識ポリシーを埋め、下のチェックリストで漏れが無いか見る。サブドメインと、既存ファイルの移行は手で。

## 手順2: ファイルを作る

`knowledge/domains/_template/` の4ファイルをコピーして埋める。`README.md`（知識ポリシーのブロックつき）、`index.md`、`intentions-log.md`、`backlog.md`。

根拠のある中身は書く。**プレースホルダは構いません。発明した事実はだめです。**

## 手順3: すべての場所に登録する（チェックリスト）

4つ全部。1つでも欠けると、ドメインは半分しか見えません。

- [ ] **`knowledge/index.md`**、2箇所: 冒頭の「現在のドメイン」の表に1行、「ドメイン目録」に1ブロック（場所・索引へのリンク・要点）。
- [ ] **`state.md`**: Tier-0 に出すべきドメインなら、稼働中の表に1行。
- [ ] **`bin/statusline.py`**: スラグと表示名を **`DOMAIN_LABELS`** に足す。`bin/menu` もこの辞書を読むので、メニューとステータスバーが同じ表を見ます。ここを飛ばすと生のスラグで出ます。
- [ ] **`bin/menu` の `LANES`**: どのレーンに属するかを足す。**番号はここから決まる**ので、足さないとそのドメインは毎回「その他」に落ち、番号が安定しません。
- [ ] サブドメインのときだけ: **親の `index.md`** が子へ案内すること。案内が無ければ子には辿り着けません。

## 手順4: 移行、既存のファイルを吸収する場合だけ

新しいドメインは、散らばっている素材を集めるために作られることがよくあります。その場合:

- **`git mv` で動かす。** 履歴がファイルに付いてきます。
- **先に、動かすファイルを指しているものを探す:** `grep -rl '<ファイル名>' --include='*.md' --include='*.py' . | grep -v '^./.git'`。そのポインタを直す。
- **History 層と一次情報層のポインタは直さない。** `intentions-log.md`、`tasks/backlog.md`、`diary/entries/`、`research/notes/` は追記専用か、書いたら不変です。**古いパスを書いたログは、書かれた時点では正しかった。** そのまま残し、どのポインタをあえて残したかをユーザーに伝えること。
- 移動元の `index.md` のファイル一覧に、**1行の「移動しました」の印**を残す。git を読まなくても足跡が見えるように。
- 参照されているだけで**まだ読んでいないファイルは、動かさない。** 新しい索引から指すだけにして、そう言うこと。
- **`git mv` は追跡済みのファイルしか動かしません。** 未追跡のものや gitignore されているもの（生の `_inbox/`、仮想環境、`.DS_Store`）は古いフォルダに残り、そのフォルダを立たせたままにします。改名のあとは `find <古いパス>` で残りを探し、普通の `mv` で移してから `rmdir`。
- **`.gitignore` に古いフォルダ名を名指しするルールが無いか確認する。** 改名すると**黙って一致しなくなり**、守られていたものが ignore から外れます。`git check-ignore -v <パス>` でルールがまだ効いているか確認できます。
- **一括改名の前に、他のリポジトリのパスに古い名前が出てこないか grep する。** 自分のリポジトリの中だけ直しても、他のリポジトリを指すポインタは壊れたままになります。

## 手順5: 検証してから締める

- [ ] `bin/menu --all` に、スラグではなく**表示名**で新しいドメインが出ること。
- [ ] コミット前に `bin/lint --diff` がきれいなこと。
- [ ] ステージは**パスを明示**して行うこと。`git add -A` や `.` は使わない。
- [ ] `intentions-log.md` の最初のエントリを書く（`closeout` スキル）。境界の判断と、あえて残した古いポインタも書くこと。
- [ ] **ブランチは同じセッションでマージする。** 立てっぱなしにしない。worktree を使ったなら `git worktree remove`。

**エージェントは既定では作らない。** `.claude/agents/<名前>.md` と登録簿の行を足すのは、名前の付いたボトルネックが実際にあるとき（繰り返し発生する、範囲の限られた仕事）だけです。

## 大事なこと

雛形は最小限で、正直に。**「まだ根拠がありません」と書いてあるドメインは健全です。それらしい事実が並んでいるドメインは危険です。**
