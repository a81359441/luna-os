# jp-email：日本語ビジネスメールを、本人の書き方で

教科書どおりのメールマナーは最低ライン。上限を決めるのはユーザーの好みで、こちらのほうが厳しい。**分かりきったことが書いてあると、読み手は「AIが書いた」と感じる。** 日本人の社会人が実際に送る、いちばん短いメールを書いて、そこで止める。

## 1. 書く前に読む

- **まずスレッド要約を読む:** `knowledge/domains/<domain>/threads/<相手>.md`（相手ごとに1つ。形は7節）。連絡先と宛名、Gmail のスレッド ID、これまでの流れ、メモ、次の一手が入っている。これがあれば、メールは**新しく届いた分だけ**開けばよく、経緯を毎回読み直さない。まだ無ければ、スレッドを一度読んで、下書きの前に要約を作る。
- 名前が分かっている相手を「ご担当者様」と書かない。要約かスレッドにある名前で宛てる。
- スレッド全体を読む。相手の温度に合わせる：相手が「〇〇さま」なら、こちらも同じ高さで。相手より堅くしない。
- このメールの**用件を一つ**決める（承諾・依頼・お断り・送付・お礼）。二つあるなら、二通に分けるかをユーザーに聞く。
- 日付が絡むならカレンダーを見る。予定とぶつかる承諾は、返事をしないより悪い。

## 2. 骨組み

```
<宛名>様

お世話になっております。<姓>です。
<一行目：相手がしてくれたことへの礼、または用件>

<本文：結論から。一〜三行>

<結び>

<姓>
```

| 部分 | 決まり |
|---|---|
| 宛名 | 続いているやりとり：`〇〇様`（姓＋様）。初めての相手：`株式会社〇〇 部署 氏名様`（「㈱」「株)」と略さない）。個人名に `御中` は付けない。 |
| 挨拶・名乗り | `お世話になっております。<姓>です。` 初めての相手：`初めてご連絡いたします。<姓>と申します。` 名乗りは姓だけ。フルネームやローマ字は使わない。 |
| 本文 | 結論が先。20〜30字くらいで、助詞の切れ目で改行。まとまりの間は空行。並ぶものが3つ以上なら箇条書き。 |
| 結び | 基本は `どうぞよろしくお願いいたします。` 依頼なら `お手数をおかけしますが、ご確認のほどよろしくお願いいたします。` 初めての改まった相手なら `何卒よろしくお願い申し上げます。` |
| 署名 | いつものやりとりは姓だけ。署名欄一式は、ユーザーに頼まれたときだけ。 |
| 件名 | 返信：`Re:` も元の件名もそのまま（`Re: Re:` は一つにまとめる）。新規：何の件で、どうしてほしいかを20字くらいで。例 `面談日程のご相談（10/5）`。 |

## 3. 決まり文句（素直な定番を使う）

- 承諾・了承：**`承知しました。`** が基準。相手がかなり堅いときだけ `承知いたしました` / `かしこまりました`。`了解しました` は使わない。
- 日程の確定：`10月5日（月）14:00、承知しました。` 開始時刻だけで足りる。終了時刻まで繰り返さない。
- 相手の手間へのお礼：`日程のご調整、ありがとうございます。` / `ご連絡ありがとうございます。` / `ご確認いただきありがとうございます。`
- ファイルを送る：`〇〇を添付いたします。ご確認のほどよろしくお願いいたします。`
- 依頼のクッション（一つだけ）：`お手数をおかけしますが、` / `恐れ入りますが、`
- お断り：`誠に恐縮ですが、今回は見送らせていただきます。` 理由は短く一つまで。
- 返信が遅れた：本文の一行目に一度だけ `ご返信が遅くなり、申し訳ございません。`

## 4. 削るものリスト（ユーザーの直し。最優先）

メールに限らず、書き手としての本人は `.claude/voice.md` にいる（あれば先に読む）。本人の直しはそこにも記録する。

見つけたら消す：

- **手順の復唱。** 「当日は時間になりましたらURLよりアクセスいたします」のように、相手が書いた案内をそのまま言い返す文。
- **読み手が推測できる含意。** 「なお、〇〇の都合上、どちらか一方となります」のような念押し。レビュー役のAIが「明示したほうがいい」と言っても、読み手は分かる前提で書く。
- **オウム返し。** 相手が書いた日時の範囲・URL・住所をまるごと繰り返すこと。
- **事務的なメールでの自己アピール。** 稼働条件・単価・自分の強みは、面談か添付資料で。
- **ユーザーが頼んでいない質問。** 本人の代わりに確認事項を足さない。
- **分かりきった形式の明示。** リモート前提の案件に「オンラインでお願いできますと幸いです」は要らない。会い方が文脈で決まっているなら書かない。
- **へりくだりの重ね塗り。** クッション言葉は一通に一つ、「ありがとうございます」も一通に一つ。

## 5. 敬語チェック

二重敬語を直す：`拝見させていただきます`→`拝見します`、`おっしゃられた`→`おっしゃった`、`伺わせていただきます`→`伺います`、`頂戴させていただきます`→`頂戴します`、`お帰りになられました`→`お帰りになりました`。`お伺いします` は慣用として定着しているので、そのままでいい。`させていただく` は一通に一回まで。

## 6. 渡し方

1. **まずチャットで詰める。** 本文はコードブロックでそのまま貼れる形で出し、補足はブロックの外、後ろに。**ユーザーが文面を確定するまで、メールソフトの下書きは作らない。**
2. 確定したら、下書きを作れる道具が繋がっていればメールソフトの下書きに作る（返信ならそのスレッドへの返信として）。繋がっていなければ、コピペできる形のままでよい。**{{AI_NAME}}は送信しない。** 送るのは人間。
   **同時に、backlog の項目に送信待ちの印を付ける:** `✉ to:<宛先> thread:<スレッドID> since:<YYYY-MM-DD>`（Gmail 以外で送るなら `✉ via:LINE since:...`）。`bin/sent-check` がこれを送信済みフォルダと照合するので、項目は「誰かが言ったとき」ではなく「メールが出たとき」に閉じる。送信済みと出たら、項目を片付けて ✉ 行を消し、スレッド要約の流れに一行足す。
3. 直すときは、スレッドへの返信として作り直して、古い下書きを消す。上書き更新の仕組みによっては、返信のつながりが外れることがある。**消す前に、古い下書きを開いて自分の版と比べる。** ユーザーがメールソフトで直していたら、その版が正しいので勝手に消さない。すでに送信済みのこともある（Gmail では、送った直後の下書き ID を消すと送信済みメールまで消えることがある）。検索結果は下書きと送信済みが混ざるので、「送った／送っていない」は送信済みフォルダで確かめてから言う。
4. いつものメールは日本語だけ。英語版は付けない。

## 7. スレッド要約を正しく保つ

ユーザーが送ったら（または新しいメールが届いて読んだら）、同じ手で要約を更新する。**流れ**に日付つきで一行、**今どこか**と**次**は書き直す（追記しない）。**メモ**には後のメールで効くことだけ。40行ほどに収め、古い流れは一行にまとめる。backlog の項目はタスクだけを持ち、経緯は要約へリンクする。要約は Connections なので、`index.md` には取り込まない。

```
# <会社／人>
連絡先: <名前と宛名>（<メール>）· Gmail スレッド: <ID> · タグ
始まり: <日付>、<きっかけ>

## 今どこか
<1〜2行>

## 流れ
- MM/DD <先方|こちら>: <何を言ったか、1行>

## メモ
- <事実、条件、確かめること>

## 次
- <次の一手と、どちらの番か>
```

日本語に限らず、{{AI_NAME}}が代わりに書くメールはすべてこれに従う: 経緯は要約から、Gmail は新しい分だけ。

## 8. 学ぶ

ユーザーが下書きを直したら、自分の版と比べる。一度きりではなく型になっている直しなら、日付を付けて4章に足す（同じコミットで）。このファイルがルールの本体。

## 出典

型は一般的なビジネスメールの解説（構成・件名・結び、返信の作法、二重敬語の一覧）から。削るものリストは、ユーザー本人の直しから育てる。
