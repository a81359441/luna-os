# ビルド

法はひとつ。**作る前に何を作るか決める。人間には結果ではなく計画を拒否させる。そして計画と出力の両方を、真実になる前に自分で批判する。** 承認時点で捕まえた間違いは一文で済み、完成時点なら1時間、世に出たあとなら信頼を失います。このスキルは安い保険です。

憲法（承認してはじめて真実、作家としての自我、可逆性）は繰り返しません。ここで足すのは、それらが含意する**ビルド特有の動き**です。計画のゲート、**2回の内向きの批判**（計画、出力）、**1回の外向きの証明**（実際に動くか）、そして進捗の追跡。

## 使うとき、使わないとき

**使う**：作るものであり、間違えると巻き戻しが高い。新しいスキル・エージェント・ドメイン構造、スクリプトや自動化、資料や複数ファイルの成果物、複数ファイルやルール層に触れるシステム変更。

**使わない**（儀式が罠になる）：`index.md` の一箇所の編集、クローズアウト、文面のドラフト、質問への回答、すぐ戻せる編集で足りるもの。

**使われる前に手順を書かない。** 誰も手でやったことのない仕事を、先にスキルや手順書にすると、推測を固めることになる。少なくとも一度は手で回し、そのあとで実際に起きたことを書き留める。

**既定の技術スタックがあるなら、ここに書いておく。** 持ち主が「ウェブは基本これで作る」と決めているなら（言語、フレームワーク、DB、置き場所、AIに書かせるための補助ツール）、この段落をその宣言に書き換える。PRD では既定から外れるときだけ、その理由を書く。決めていないなら、この段落は消してよい。

判定：*1時間後に「違うものを作っていた」と分かったら嫌か？* ノーならそのまま作る。イエスならこの弧を通る。

**大きさに合わせる。** 小さなビルドは全工程を数行と一段落の自己批判で通す。大きなものはPRDもリスク検討も実物にする。弧は**順番**であって、書類のノルマではありません。

## 弧

**理解 → PRD → 計画リスクの検討 → 承認 → 構築 → 自己レビュー → 検証 → 締め**

### 1. 理解（分かるまで計画しない）
何を計画しているのか本当に分かるまで、計画を書かない。未解決の問いを**先に**全部出し、ほぼ確信できるまで聞く。途中で発見することになる論点は、今なら最も安い。ここがAIが価値を出す場所です。人間が見ていないケースが見えるから。

### 2. PRD（作る前に書く）
規模に合わせて、必要な項目だけ。
- **課題**：何が足りない・壊れているのか、1〜2行。
- **成功条件**：正しいとどう分かるか（観察できる形で。雰囲気ではなく）。
- **範囲**：入るもの、そして**明示的に入らないもの**（この行が膨張を止める）。
- **制約**：家の作法、境界、壊してはいけないもの。
- **手順**：順番に。時間が絡むなら各段の目安も。
- **可逆性**：どれくらい戻しやすいか。

**作家としての自我はここで使う。** 依頼が戦略と噛み合っていない、技術的に間違っている、過去の決定と矛盾しているなら、1行も作る前に言って、より強い案を出す。

### 3. 計画リスクの検討（1回目の内向き）
承認を求める前に、計画そのものに刃を向ける。**どの項目が最も正しさ・境界・製品のリスクを持ち込むか。** 高い順に並べ、それぞれに手当てを足す（順番を前に出す、試作する、チェックを足す、範囲を狭める）。計画はもっともらしく見えて、一番危ない項目を平然と隠します。ここがまだ無料で直せる最後の場所です。

### 4. 承認（作る前に、明示的に）
PRDとリスク一覧の両方を見せる。明示的なゴーをもらう。未解決の問いは先に潰す。人間には**結果**ではなく**計画**を、安く拒否させる。

*可逆性ゲートの例外*：ブランチ上の新規ファイルのように**簡単に戻せる**ものは、同じターンで作ってから見せてよい。そうしていることと理由を述べる。ゲートは戻しにくい行為だけを止めるもので、安いものを止めるためのものではありません。

### 5. 構築（可逆性ゲートを効かせ、進捗を残す）
- **可逆性ゲート**：戻しにくいこと（真実のファイルの上書き、削除、送信、公開、破壊的コマンド）の前で必ず止まって確認する。質問で中断するほうが、黙って壊すより常に安い。
- **中断されても残る形で進捗を追う**：セッション内の多段ビルドはタスク機能で、セッションをまたぐものは `tasks/backlog.md` に。
- **決定は作りながら記録する**（雑務ではなく副産物として）。
- **黙って削らない**：範囲を狭めた、サンプリングした、飛ばしたなら言う。黙った省略は「全部やった」と読まれます。

### 6. 自己レビュー（2回目の内向き）
コミットや締めの前に、懐疑的な他人として自分の出力を見る。重大な順に並べ、直す計画を作る。**そのビルドの種類に効く失敗**を見る。
- **コード・スクリプト** → バグ、論理の不整合、非効率、端のケース。
- **知識の成果物**（索引、ドメイン文書、ノート） → 根拠のない主張、壊れた出典、境界の漏れ、索引と矛盾する古い事実。
- **資料・レンダリング物** → 真実ファイルから外れた記述、機微な内容の混入、出典に辿れない主張。
- **スキル・ルールの変更** → `CLAUDE.md` と矛盾しないか、既存スキルと重複しないか、使わない場面を書いたか。新しいスキルなら、英語の `name:` と `description` 末尾の `日本語：「名前」「別名」` の**両方**を付けたか。

### 7. 検証（外向きの証明）
自己レビューは欠陥を**推論**します。検証は**観察して証明**します。読み返すより、実際に動かして確かめるほうが品質は上がります。**証明なしに完了と言わない。直したら必ず再テストする。**
- **コード・スクリプト** → 実際に走らせる。普通の入力と端の入力の両方で。ソースを読むだけにしない。
- **知識の成果物** → 冷えた目で読み、それが答えるべき本当の問いを投げる。答えられるか。出典がすべて解決するか。索引から**辿り着けるか**。
- **資料** → 開いて見る。表示と読みやすさを確認する。
- **スキル・ルール** → 実際に発火するか試す。新しいドメイン構造は `self-diagnose` を通るか。

規模に合わせる。小さければ「走らせた、出力は正しい」の一行。大きければ成功条件ごとに、**観察したこと**を述べる。今は検証できないなら、そう正直に言う。できたふりをしない。

### 8. 締め
`closeout` を走らせる。索引に届かないビルドは、システムが忘れる仕事です。

---

> 弧は順番であって、書類のノルマではありません。小さいビルドなら各段も小さく。ただし、痛むほど大きいビルドでは、どのゲートも飛ばさないこと。
