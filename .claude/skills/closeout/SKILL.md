# クローズアウト

**締めの動詞はこれ1つだけです。** 以前は `end-session` という別のスキルがありましたが、統合しました。`closeout` と言うか `end-session` と言うかを、**疲れて立ち去る瞬間に**思い出せるかどうかに依存する手順は、走りません。

## 出口は2つ：完了か、続けるか

まず一行で聞く（答えが明らかなら聞かない）：**この仕事は終わったか、それとも保存して続けるか？**

- **完了** → 下の5つの動作をそのまま。
- **続ける** → 仕事は終わっていないが、文脈がいっぱい（`context-meter` フックが18万前後で知らせる）か、話が逸れてまっさらから始めたい。以前の `checkpoint` スキルはここに統合した。「どこまでやったか保存する」と「締める」は同じ瞬間の2つの動詞で、しかも checkpoint は状態を git 管理外のフォルダに置き、それが古びていったから。速く、儀式なしで：
  1. **次の一手を、仕事がもともとある場所に、先に残す**（commit より前に）：ドメインの `backlog.md` の項目を `[~]` にし、本文に `next:` の行（戻ったとき最初にやることを正確に）と `branch: <名前>` を書く。途中で決まったことや、新しいセッションが聞き直してはいけないことも同じ項目に。項目がまだ無ければ作る。これが git に残る正本で、ローカルのポインタにしか無い情報を作らないこと。
  2. **途中の仕事を、その backlog の変更と一緒に commit して push する**（パスを明示、`git add -A` は使わない）。ステージした差分を見て、両方が入っていることを確かめる。push は同じ名前のブランチへ明示する（例 `git push -u origin HEAD:refs/heads/<ブランチ>`）。引き継いだ `origin/main` の上流に押さないこと。**マージも掃除もしない**：半分の仕事は真実にしない。掃除は終わるセッションのためのもの。
  3. **保存できたと言う前に、リモートを確かめる**：`git rev-parse HEAD` と `git ls-remote --exit-code origin refs/heads/<ブランチ>` の SHA が一致すること。その commit に backlog の引き継ぎが入っていて、このセッションの未コミットの変更が残っていないこと。push の失敗、ブランチが無い、照会の失敗、SHA の不一致はどれも**未確認**：ローカルの仕事はそのまま残し、どこで失敗したかを伝え、再開ポインタは作らず、`/clear` してよいとも言わない。原因が直ったらやり直す。force-push はしない。
  4. **確認が取れてから、ローカルの近道ポインタを `.session/resume-pending` に書く**：3〜6行で、ドメイン、ブランチ、確認した commit、backlog 項目（パス＋題名）、`next:`。ステータスバーの話題も更新する。`session-resume` フックが /clear のあと一度だけ注入して消す。ここより前で中断しても、失うのは近道だけ。引き継ぎはもうリモートのブランチにある。
  5. 一行で伝える：*「`<ブランチ>` に保存して確認しました。`/clear` すれば〈次の一手〉から続けます。」* `/compact` より `/clear` を勧める。引き継ぎは正確で、compact の要約は欠ける。

  この流れを変えるときは、[再開の確認手順](references/continue-recovery.md)をやり直す。確かめられるのは保存とフックの届き方で、AIが手順どおりに動いたことの証明にはならない。

  **ポインタ無しの `resume`**（完全なクリアのあと、または数日後）＝ `bin/menu --resume`：`next:` を持つ `[~]` の項目すべて（ただの `[~]` は「返事待ち」の意味でも使うので、再開できる印は `next:` のほう）。これは今のチェックアウトしか見ない。保存したはずの項目が無ければ、保存先のリモートのブランチを（必要なら fetch して）開き、そこの backlog を読む。迷うときは選んでもらい、ローカルの変更を上書きせずにそのブランチに移り、`next:` を読んで続ける。あとでその仕事を**完了**で締めるときは、`next:` の行を消して一覧から外す。

動作は5つ、この順番で。途中でやめても構いません（まだ続きがあるなら）。ただし**コミット済みの仕事をローカルのブランチに置き去りにすること**だけは、どの場合でもしないこと。

1. **ブリーフ**: 開いているものを片付け、次の一手を書き直す。
2. **コンパイル**: 統合層が「今の真実」を吸収する。
3. **ログ**: 監査記録が「何が起きたか」を残す。
4. **着地**: ブランチをマージして push する。
5. **掃除**: 条件に当てはまるものだけ。

**締めるかどうかは、言葉ではなく{{AI_NAME}}が判断する。** 引き金は*このセッションでドメインの「今の真実」が変わったか？*であって、*セッションがあったか*ではありません。真実が変わったなら頼まれなくても締めを提案する。ユーザーが「締めて」と言っても、全部もう書かれている、あるいは何も変わっていないなら、理由を添えてそう言い、空の儀式は飛ばす。

チャットは使い捨て、索引は生きた真実、ログは領収書。**ログだけ書いて終わる締めは、システムを1ミリも賢くしません。**

## 1. ブリーフ、開いているものを片付ける

スタートメニューは**ブリーフ**であって、ドメインの目次ではありません。`bin/menu` はその大半を計算します（今日の予定、各 backlog に立っている締切、進行中のもの）。でも**ファイルが正しい分しか正しくなれない**し、唯一計算できないのが「次に何をするか」です。両方を直せるだけの文脈と理由が揃っているのは、締めの瞬間だけ。ここを飛ばすと、ブリーフは静かに「先週の緊急」の一覧に腐ります。

**この動作は、端末以外の surface もまとめて書いています。** `bin/menu --json` を読む通知や push があるなら、ここで片付けたものがそのまま向こうに出ます。**別立ての「朝用ファイル」を作らないこと。** 誰も更新しないので必ず腐ります。端末には出して外には出したくない項目は `🔒` を付けます。

- **最初に `python3 bin/sent-check` を走らせる。** 送信待ちの項目を一覧にし、Gmail の送信済みフォルダに出たかを聞く。`✔ 送信済` はどれも状態の変化なので、項目を片付けて `✉` 行を消し、スレッド要約を更新する。`? 要確認`（LINE やサイト経由）は、ユーザーに聞く一つの質問。送ったメールが何日も「送信待ち」のまま残ったことから生まれた。
- **1件ずつ、終わったか終わっていないかを決める。** このセッションが触った backlog の項目について、想像ではなく明言する。終わった → `[x]` と今日の日付。途中 → `[~]` のまま、本文を「**残り**は何か」に書き直す（「こうしたい」ではなく）。終わったと見なしてよいか本当に分からないなら、聞く。それこそ締めが存在する理由です。
- **セッションの積み残しを backlog へ流す。** 浮かんだが終わらなかったものは、ログに願望として書かず backlog へ。既定は `knowledge/domains/<domain>/backlog.md`、本当に横断するときだけ `tasks/backlog.md`。書式は `docs/backlog規約.md`。
- **日付が動いたら、両方で直す。** 締切がずれたら backlog の `⏰` を直し、**カレンダーの予定も動かす**（`python3 bin/gcal/gcal.py move <キー> --date YYYY-MM-DD`）。**片方だけ正しい状態は、両方無いより悪い。** ブリーフは backlog を読み、カレンダーアプリは予定を読み、外に出る surface は両方を読むからです。`⏰` は `YYYY-MM-DD` の絶対日付で、**それ自身の行に**書くこと。そうでないとブリーフは順位を付けられず `⏰日付なし` に落とします。
- **明日の「今日の一点」が無ければ入れる。** `python3 bin/gcal/gcal.py add "今日の一点: <何を>" --date <YYYY-MM-DD> --start HH:MM --purpose focus --source <domain>/backlog.md`。1日1つ。翌朝のブリーフの「今日」に、**その予定がそのまま**一日の軸として出ます。
- **`state.md` の `## Now` を、ブリーフの「忘れずに」として書き直す。** **最大3つの短い箇条書き、1つにつき1つのこと。** 書くのは、カレンダーと「今週」には**出せないもの**: 日付の無い大事なこと（時間のかかる勉強、ゆっくり進むプロジェクト）、返すべき返事、振り返る価値のあること。**予約済みの予定や、日付のある backlog 項目を繰り返さないこと。** ここを一段落の「今週の焦点」にすると、すぐ上の「今週」の言い直しになり、誰も読まなくなります。日付があるものは、ここではなく `⏰` つきで backlog へ。このセッションで実際に出た具体的なことを書き、ありがちな格言は書かない。**余白を残す**: スクリプトが計算した一押し（日記が止まっている、など）を1つ足すことがあるので、それが出ている日は2つにする。**追記ではなく書き直す**こと。ここは Now 層であってログではありません。ブリーフの中で唯一の「判断」です。
- 最後に `python3 bin/menu --refresh` を走らせてブリーフを読み返す。**明日ユーザーに言いたいことがそこに出ていなければ、悪いのは表示ではなくファイルです。**

## 2. コンパイル、統合層を先に更新する

ドメイン README の**知識ポリシー**を読む。このドメインが*どう*コンパイルするかが書いてあります。そのうえで問う。*この仕事はドメインの「今の真実」を変えたか？*

- 変えたなら `index.md` を更新する（クイックリファレンス、状態の行、数字、古くなった記述）。この仕事の**あと**の現実を映すこと。**下に日付つきメモを追記するのではなく、書き換える。** 既存のセルに日付つきの訂正を積むのは、表の格好をした追記ログです。
- 横断の状態や優先順位が動いたなら `knowledge/index.md` のその行と `state.md` も触る。
- 恒久的には何も変わっていない（純粋な実行で、新しい事実が無い）なら、それを1行で述べて 3 に進む。

## 3. ログ

- **書き込む先を決める。** 仕事が触ったドメインの `knowledge/domains/<domain>/intentions-log.md`。迷ったら聞く。
- **backlog は動作1で片付け済み。** ここで再び流さないこと。開いている項目をログに書き写さないこと。**ログは起きたことを、backlog はまだ終わっていないことを持ちます。**
- **backlog を `index.md` に取り込まない。** Connections であって統合ではありません。索引はそこへ**案内する**だけ。
- **既存のログを読む。** 書式と並び順を合わせる。
- **3〜6項目だけ。** 結果（何をしたか・何が決まったか）・ファイル（パス、ブランチやコミット）・境界（宣言→タグ→確認の判断: `#個人` `#商用` `#発信` `#複合` `#システム`）・学び / 次（本当に役立つときだけ）。
- **今日の実際の日付を使う。** 推測しない。分からなければ聞く。
- **ログが長くなったら退避する。** 書き込む先のログが30件ほどを超えたら、90日より古いエントリのうち**その事実がすでに `index.md` にコンパイルされているもの**を、同じフォルダの `intentions-log-archive.md` へ、そのままの文面と順番で移す（履歴は追記専用なので、移すことはできても要約はできない）。真実が索引に届いていないエントリは残す。それが唯一の写しだからです。
- **事実だけ。** 起きなかったことは書かない。内容が大きいときは、書く前に見せて承認をもらう。

**そのあとセッション台帳に1行追記する**（`tasks/sessions.md`、システム用のドメインを作ってあるならそちらの `sessions.md`）。ここが**セッションを「セッションとして」記録する唯一の場所**です。`intentions-log.md` はドメインごとなので、6ドメインに触れた仕事は6ファイルに散り、「火曜日に何があったか」に答えるものが無くなります。追記専用、History 層、1行:

```
| <YYYY-MM-DD> | `<短いid>` | <1行: 何が出たか> | <触れたドメイン> | <コミット数> |
```

`<短いid>` は `bin/session-id` の先頭8文字。**何も出力されないハーネスでは、でっち上げずに行ごと省く。** 結果は1行に留めること。`bin/sessions` がこれを Claude Code の記録と突き合わせて `h` の履歴を作りますが、**何を「訊かれた」かは記録の側が持っている**ので、ここが持つのは**何が「出た」か**だけです。1セッションで2回目の締めなら、**行を足さずに既存の行を更新**すること。

## 4. ブランチを着地させる

締めるということは仕事が終わったということなので、ブランチを漂流させないこと。

- 承認済みのトピックブランチ → **`--no-ff` で `main` にマージして push**、そのあとブランチを削除（ローカル、push してあればリモートも）。個人のナレッジ・リポジトリではこれが既定。共有の台帳ファイル（`state.md`、`knowledge/index.md`）の衝突は**両方を残して**解決する。ほぼ常に足し算だからです。
- 真実になる前にレビューを挟みたい → 代わりに **PR を作り**、ブランチは残す。
- すでに `main` → **push するだけ**。
- worktree を使った → マージのあと `git worktree remove`。

**未承認の仕事を黙ってマージしないこと。** 承認してはじめて真実、は生きています。どれに当たったかを1行で述べる。

**検証はコミットの「前」にやる。** 仕事が本物だと示す確認を先に走らせること（`bin/lint --diff`、ドメインを変えたなら `bin/menu --all` で表示名つきで出るか）。**コマンドの連鎖の最後に置いた検証は、手前で何か失敗した瞬間に飛ばされます。**

## 5. 掃除、条件に当てはまるものだけ

どれも何度実行しても安全です。1セッションで複数回締めてもうるさくなりません。2回目は何もしません。

- **取り残されたブランチは？** `git branch --no-merged main` と `git branch --merged main`。マージ済みのものは **`git branch -d`** で削除（ローカルとリモート）してから `git fetch --prune`。**`-D` は絶対に使わない。** 削除を拒否されたら未マージのコミットがあるということなので、勝手に処理せず、出して聞くこと。
- **きれいな状態か？** `main` にいて、ツリーがきれいで、origin と同期していること。`git status --porcelain` が空であること。1行で報告する: ブランチ、ツリー、同期、着地したブランチ数。
- **このシステムを他の人にも配っているなら**（テンプレートとして clone させている、家族や同僚が同じ構造を使っている）、`CLAUDE.md` `.claude/skills/**` `.claude/agents/**` が変わったかを見る。変わっていたら、向こうが吸収できる形にしてから締めること。**運用層の変更は、伝わらなければ自分1人の改善で終わります。**

## 書式

```markdown
## <YYYY-MM-DD>: <短いタイトル>

- **結果**: ...
- **ファイル**: ...
- **境界**: ...
- **学び / 次**: ...
```

落ち着いて、簡潔に。1回の締めにつき1エントリ。**ダッシュは使わない**（`CLAUDE.md` のハードルール）。
