# アジェンダ

日々の予定を、ほぼ摩擦ゼロで最新に保ちます。ユーザーは移動中に一言投げてくるだけ。それを日次ログのきれいな1行に変えるのがこちらの仕事です。チャットは使い捨て、`agenda.md` が生きた記録です。

**ファイル**：個人系ドメインの `agenda.md`（例 `knowledge/domains/personal/agenda.md`）。無ければ最初の実行で作り、ドメインの `index.md` から案内を1行張る。

このファイルは**Connections（揮発）**です。統合層にコンパイルしないこと。日々の予定は1年後には無価値です。

## 2つのモード

**読む**（「今日なんだっけ」）→ 今日のブロック（必要なら明日も）を2〜4行で報告する。ファイルを整形し直さない。

**更新する**（何か変わった）→ 反映する。

1. **まず `agenda.md` を読む**（書式と並び順に合わせる。新しい日が上）。
2. **該当する日のブロックを見つけるか作る。** 1ブロックはちょうど3行：**予定 / 記録 / メモ**。短く、文ではなく句で。
   - キャンセル → 予定の行を `~~...~~ 中止` にする。消さない（履歴が価値）。
   - 新規・変更 → ブロックを足すか動かす。今日を上に、日付順を保つ。
   - 「これをやった」「これを撮った」 → **記録**の行を埋める。
3. **波及を書く。** 変更が他に響くとき（時間が空いた、締め切りが危うい、疲れが残る）は**メモ**に短い句で1つだけ。説教しない。
4. **恒久的な予定に触れる変更**（旅程や複数日にわたる計画）なら、その計画ファイルも更新して「最終更新」を直す。日々のノイズは `agenda.md` だけに留める。
5. **今日の実際の日付**を使う（推測しない）。曜日も入れると一覧しやすい。
6. **事実だけ**。言われていない予定・結果を書かない。
7. **コミットしてpush。** 小さな事実の更新なので `main` に直接コミットしてよい。ローカルに残さない。

## 書き方

落ち着いて、最小限に。一言入れたら一行きれいに出る、それだけの価値です。もし変更が「予定の調整」ではなく「実際の判断」なら、それを指摘して `closeout` を提案します。
